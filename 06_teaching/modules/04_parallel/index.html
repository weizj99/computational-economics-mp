Unit 04 · Eight short lessons, three of them optional

Parallel computing and acceleration

Make the same model computation cheaper. Each short lesson starts with fixed inputs, makes one change, checks what must stay the same and ends with a result you can write down. Each has a one-minute film and points to the code that does the work. Lessons 01, 02, 03, 06 and 08 are the core. Lessons 04, 05 and 07 are optional: their code uses GPU kernels written in Triton, and you can skip them on a first reading.

The code independently implements an economy based on De Loecker, Eeckhout and Mongey (2026). The acceleration examples and benchmark measurements were produced for this course.

01 / Execution

Five ways to organize the work

Follow each change from the work it saves to the work that remains. Each film is one minute, with English narration and captions.

Parallel workers

Each candidate economy has its own parameters and returns its own moments. Give independent economies to separate workers: a worker can start its next job while the others are still solving theirs.

What is removed?
The wait for one independent economy to finish before another can begin.
What remains?
Every economy must still be solved in full. Setup, the final join and uneven job lengths can limit the gain.
# Each call solves one independent economy.
results = pool.map(solve_economy, candidates)
moments = collect_in_candidate_order(results)

Two reasons the gain falls short of the worker count. The jobs have different lengths, so lanes stand idle near the end: if the 24 units of work split evenly, four workers would finish at 6 units, but the last job ends at 7. And the 2 units of setup and 1 unit of join take the same time with any number of workers, so with serial work the speedup can never exceed 27 / 3 = 9.

Vectorization

Put firms in rows and markets in columns. One array expression applies the same operation across the matrix; a sum along the firm axis still gives a separate total for each market.

Given
One economy’s firm values, arranged as M rows and J market columns, with inactive firms masked out.
Change
Follow the film from separate market calls to one matrix operation. Trace one column through the firm sum and normalization in the code below.
Check
The sum runs down firms, not across markets. Every nonempty market’s shares sum to one; each market keeps its own convergence state.
Record
Label the shapes of the input, market totals and output. Explain which repeated calls disappear and which arithmetic remains.
# weights has shape (firms, markets).
market_totals = weights.sum(axis=0, keepdims=True)
shares = weights / market_totals

Vectorization changes how the work is written. This array code still runs on one CPU core; workers and GPUs are separate steps, in lessons 01 and 03.

Time it: python lessons/04_parallel/loop_vs_vectorized.py solves the same 2,000 markets in one call and in one call per market, with 5 to 80 firms per market, in about 30 seconds.

▶60-second explanation · EnglishVectorization: from market calls to an array⌄

Follow four market calls into a firms-by-markets matrix. Watch the column sums and normalization preserve each market's boundary.

Read the English transcriptDownload video with captions

Check your result
  • Shapes. Weights (M, J): one row per firm, one column per market. Market totals (1, J) with keepdims=True. Shares (M, J).
  • Reduction axis. axis=0, down the firms of each market, so each column keeps its own total. A sum along axis 1 would mix markets.
  • What disappears. The J separate calls to the share solver, one per market, and the overhead of each call. What remains. The same arithmetic for every firm, the firm sum in each market and the share iterations. Each market keeps its own convergence test: working = ~done freezes the markets that have converged while the others continue.
  • Timing. Both versions give the same shares up to rounding and the same iterations in every market. The loop's time hardly changes with M; the vectorized time grows with it. So the speedup falls as M rises: on one core, from about 240 times with 5 firms to about 20 times with 80. Your times will differ, but the speedup will fall the same way.

GPU batching

Stack compatible economies into a B × M × J array. A GPU operation can then work across many economies and markets, with a separate active mask for the parts that still need to converge.

Given
Fixed candidate rows and saved draws. Economies with the same M = floor(N) can share a B × M × J batch.
Change
Follow the film as separate economy matrices enter one batch. Give each launch more work, and keep track of which parameters and result belong to which economy.
Check
A finished market stops updating while others continue. Every economy still goes through both periods, every exit round and every root solve. The batch must fit in GPU memory.
Record
Draw the three axes and mark the active mask. Propose two batch sizes to compare, with the same rows and checks, and a clock that covers the whole solve.
# B economies × M firms × J markets.
state = stack_compatible_economies(economies)
state = update_active_markets(state, active_mask)

A larger batch helps while it fits in memory and keeps the GPU busy. Compare batch sizes by timing the whole solve.

Kernel fusion

Optional lesson: its code uses GPU kernels written in Triton. The core lessons are 01, 02, 03, 06 and 08.

A chain of small GPU operations can write a temporary array to device memory, then read it back in the next operation. A fused kernel combines compatible operations so intermediate values can stay inside the kernel.

Given
The same input array and a chain of compatible operations. The unfused version writes an intermediate array to device memory.
Change
Trace the separate operations in the film, then the fused kernel. Cross out the temporary-array write/read and launch that fusion can remove.
Check
The required arithmetic and reductions still happen. Retain the intended precision, damping, masks and residual checks; compare outputs before timing.
Record
A before/after diagram of launches and memory traffic. Name the saving for the share update alone.
# Separate operations materialize a temporary array.
temporary = scale * x
y = temporary + offset

# A compatible fused kernel computes the same expression.
y = fused_scale_and_add(x, scale, offset)

Fusion changes how the work runs and how much it reads and writes in memory.

Find this in the source

In the current source, compare 03_gpu/qmp_torch_current.py::_share_step with 03_gpu/qmp_torch_share_fused.py::share_step_fused and _share_step_kernel. The real kernel fuses one whole share update, including the sums over firms; the film’s scale-and-add example is a simpler case. The convergence loop stays outside the kernel.

Pause on each version. Count the depicted launches and temporary-memory trips; keep the required operations on both drawings.

▶60-second explanation · EnglishKernel fusion: fewer trips to memory⌄

Read the English transcriptDownload video with captions

Check your result
  • Before. Two launches. The first reads x and writes the temporary array to device memory; the second reads the temporary back and writes y.
  • After. One launch reads x and writes y. The temporary value stays inside the kernel, so one launch, one write and one read of a full array disappear. The multiplication and the addition both still happen.
  • The checks. On the same inputs, shares, markups, masks and residuals agree with the unfused share step within the original tolerances. Then time the full solve, once the checks pass: only the share update gets cheaper, so the full solve speeds up by less than the share step.

Resident iteration

Optional lesson: its code uses GPU kernels written in Triton. The core lessons are 01, 02, 03, 06 and 08.

When the host checks every small iteration, it may repeatedly wait for the GPU and launch the next step. A resident inner loop keeps state and compatible stopping checks on the device through that sequence.

Given
The same share state, FP32 predictor and FP64 correction budget as the mixed backend.
Change
Follow one correction step in each film lane. Move the correction loop and its stopping state onto the GPU, reducing host checks and relaunches.
Check
Each step still uses the previous state. Preserve each market’s first stopping step, masks, iteration cap, failure path and independent final FP64 residual.
Record
Mark where state lives and where the host waits in both versions. Name one removed handoff and one dependency that remains.
# Inside the resident kernel, with the original stopping rules:
while any(active) and iteration < iteration_cap:
    state = update_active_markets(state, active)
    active = original_remaining_work_mask(state)
    iteration += 1
return state, convergence_status

Only the inner share loop moves onto the GPU; the output root, the exit rounds and the rest of the economy run as before. Each update still needs the one before it.

Both return to the independent _share_residual check. The optional resident_backend is documented in docs/GPU.md.

  • Host-driven. The share state stays on the GPU, but at each stopping check, every fourth update in the mixed backend, the host waits for the GPU, reads the result and launches the next updates.
  • Resident. The loop and its stopping checks run on the GPU. The host launches it once and waits once, at the end.
  • Removed handoff. The host’s wait and relaunch at each stopping check. Remaining dependency. Each update still needs the state from the previous one, and the returned shares still pass the independent FP64 residual check before prices, the output root and the exit decision use them.

Predict cheaply, then correct strictly.

Optional lesson: its code uses GPU kernels written in Triton. The core lessons are 01, 02, 03, 06 and 08.

A low-precision share prediction supplies a starting point. The high-precision correction and independent final check decide whether the answer is acceptable.

Given
The same FP64 inputs and final acceptance rules. Only a preliminary share prediction may use FP32.
Change
Follow the prediction into FP64 correction and a fresh residual check. Trace the fallback to the original FP64 initialization when the prediction is unusable.
Check
Deduct the predictor budget from the total cap. Retain the original correction tolerance; prices, roots, fixed costs, exit decisions and moments remain FP64.
Record
Annotate the flow with each stage’s precision and acceptance check. Explain why a small FP32 predictor residual cannot certify the final answer.

Pseudocode

prediction = predict_shares_fp32(inputs)
start = usable_fp64_start_or_original(prediction)
shares = correct_shares_fp64(start, original_tolerance, remaining_budget)
check_independent_fp64_residual(shares)
# Continue prices, roots, exits and moments in FP64.

The predictor can change the path and the number of iterations compared with an all-FP64 solve. The FP64 checks decide whether the final result is accepted.

▶60-second explanation · EnglishMixed precision: a predictor is not the final answer⌄

Follow an FP32 share prediction into FP64 correction, a fresh residual check and the remaining FP64 economy.

Read the English transcriptDownload video with captions

Check your result
  • FP32 prediction. At most 16 share updates with a looser tolerance. It only proposes a starting point.
  • Usable start, FP64. The prediction is converted to FP64 and normalized. Where its shares or market totals are not finite and positive, the market restarts from the original FP64 initialization.
  • FP64 correction. The original update rule and tolerance, with the 16 predictor updates deducted from the iteration cap.
  • Independent FP64 check. The residual of the returned shares is computed again and must meet the original tolerance, together with the recorded stopping residual, the iteration cap and finiteness. Prices, the output root, fixed costs, exit decisions and moments stay in FP64.
  • Why FP32 cannot certify the answer. FP32 keeps about seven significant digits, so its residual cannot show that the shares meet the FP64 tolerance of 10−10. Only the FP64 check of the returned shares can.

06 / Code and resources

Run the CPU and GPU code

Built from the course repository

The current source bundle contains the CPU model and tests, the batched GPU solver, optional fusion, mixed-precision and resident variants, and a single-economy GPU reference. Its lessons/04_parallel folder reruns this unit’s experiments: the CPU worker timings, the two short exercises and the GPU checks against the CPU solver.

Current CPU + batched GPU source ↓

Start with the README and python run.py --help inside the bundle. CPU: Python, NumPy and SciPy. GPU: a CUDA-capable PyTorch environment; fused variants also need Triton.

Try it yourself

Time the CPU workers on your computer.

Download the current source, unpack it, and run this command in the unpacked folder or at the root of the course repository. It needs Python 3.10 or later with NumPy and SciPy. On four cores it takes about four minutes.

python lessons/04_parallel/scaling.py --cases 16

The script solves the first 16 of the 256 timed economies with 1, 2, 4, … worker processes, up to the number of cores, each with one linear-algebra thread. It times each pool from start-up to shutdown and compares every result with unit 03’s saved values. Without --cases 16 it solves all 256, as in the earlier CPU recordings; one worker then takes about 20 minutes.

Check your result

Every line should end with “matches saved results: True”. The times depend on your computer; on the four-core computer used to test this page:

 1 workers:    128.4 s   matches saved results: True
 2 workers:     68.2 s   matches saved results: True
 4 workers:     37.7 s   matches saved results: True

Compare your speedups T(1)/T(W) with the earlier CPU recordings rather than with the worker count. Here they are 1.9 with two workers and 3.4 with four. The recordings of all 256 economies reached 2.02 and 4.01, because start-up takes a smaller share of a longer run.

On a computer with an NVIDIA GPU and PyTorch, python lessons/04_parallel/check_gpu.py checks the GPU code against the CPU solver; its last line should read “All GPU checks passed.”

What did the earlier CPU worker recordings measure?

The first 256 candidate economies for the year 2000, with 10,000 markets and two periods. Every run uses the same inputs, numerical precision and fixed-cost rule.

Wall time includes process-pool startup, draws, solving, result writes and shutdown. Waiting for the machine and setting it up are outside the clock. Each worker uses one numerical-library thread and a different physical core.

Each is a single timing on one shared machine, so the variation between repeated runs is unknown.

This is exercise 6 of unit 03. In the download, lessons/04_parallel/scaling.py runs it again on your machine.
